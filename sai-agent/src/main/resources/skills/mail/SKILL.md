# 邮件技能（mail）

本技能由 **EmailAgent（邮件中枢子智能体）** 调用，统一管理邮件的「接收 → 解析 → 委派 → 发送」全链路。收发只通过两个工具完成：`receive_mail`（收）、`send_mail`（发）。

> ⛔ **发送铁律（最高优先级）**：邮件写好之后**先给用户预览**，**只有用户明确确认发送，才可以调用 `send_mail`**。任何情况下都不得跳过预览直接发送，包括用户一上来就说“帮我发封邮件给某某”。

## 触发条件
- 接收：用户要求“检查/收邮件/收件箱有什么新邮件/读取最新邮件”；或定时流程把新邮件交给 EmailAgent 处理；
- 发送：用户要求“发邮件/发个邮件/邮件通知/邮件提醒/把XX发到邮箱” → **一律进入两阶段流程（先出草稿，见 §四）**；
- 解析与委派：收到邮件后，需要把正文结构化、并拆解为可执行任务交给其他子智能体。

## 一、接收邮件：receive_mail
参数（均可选）：
- `max`（可选）：最多拉取邮件数，默认 10。

返回结构化 JSON 邮件列表（每封含 `from` / `fromName` / `subject` / `content` / `hasAttachment` / `attachCount` / `sentDate` / `messageId`）。
> 邮件服务未配置（`spring.mail.receive.host` 为空或账号/授权码为空）时，`receive_mail` 返回“邮件接收服务未配置”提示——据实转告，不要假装已收到。

## 二、解析为 JSON（接收后的标准动作）
收到邮件（无论是 receive_mail 拉取还是调用方直接提供原文）后，先将其解析为结构化 JSON，至少包含以下字段，便于下游拆解：
```json
{
  "from": "发件人邮箱",
  "fromName": "发件人显示名",
  "subject": "主题",
  "content": "纯文本正文",
  "intent": "一句话意图（如 求助/通知/待办/咨询/营销/垃圾）",
  "urgency": "high | normal | low",
  "hasAttachment": false
}
```
仅输出该 JSON（不要多余解释），随后交给 **EmailTaskAnalyzer** 子智能体拆解任务。

## 三、委派拆解：EmailTaskAnalyzer
拿到邮件 JSON 后，显式请求：「请使用 EmailTaskAnalyzer 子智能体，将上述邮件 JSON 拆解为可执行任务列表」。
EmailTaskAnalyzer 会产出每条任务的 `title` / `description` / `targetAgent` / `targetSkill` / `priority` / `needReply`。
任务清单随后由 **主 Agent 分发给对应的子智能体执行**；其中 `needReply=true` 的回复类任务，回到 EmailAgent **起草回信草稿并交用户确认**——草稿阶段不发送（见 §四）。

## 四、发送邮件：两阶段「草稿 → 用户确认 → 发送」

### 阶段一 · 起草稿 + 预览（默认动作，禁止调用 send_mail）
1. 整理出四个发送要素：`to`（收件人）/ `subject`（主题）/ `content`（正文）/ `html`（是否 HTML）；信息不足就先简短问齐，不要猜；
2. 正文按 §六 的 3KB 上限裁剪；
3. **不要调用 `send_mail`**，只输出下面这个草稿块（字段顺序固定，便于用户逐项核对，便于主 Agent 原样呈现）：

```
收件人：xxx@xx.com
主题：xxx
格式：纯文本
正文：
<正文原文，完整贴出>
```

> **草稿块必须干净**：块内**只允许出现上列四项**，块外**不要再加任何别的话**。
> - **不要**加标题（如「【邮件草稿 · 待确认】」）、**不要**加分隔线；
> - **不要**显示字节数或「上限 3072 字节」之类的限制提示（§六 的 3KB 上限照常在**内部**检查，只是不写出来）；
> - **不要**写「确认无误请回复『确认发送』/要改哪里直接说」之类的提示语；
> - **不要**加说明、备注、小结，**不要**在块外复述收件人/主题，也不要罗列内部流程；
> - 正文必须让用户**完整看到**，不得只给摘要或“……”省略，否则用户无法确认。
> - 用户对草稿提出修改后，重新走一次阶段一（同样只输出这一块），再等一次确认。

### 阶段二 · 明确确认后才发送
- **算确认**（满足其一）：用户回复了明确许可，如「确认发送 / 发送吧 / 可以发 / 就这版发 / 没问题发出去 / OK 发出去」；或派发指令里显式写明「用户已确认发送」；
- **确认后由主 Agent 带着定稿派发**：主 Agent 应把用户确认过的完整草稿（收件人 / 主题 / 格式 / 正文）连同「用户已确认发送」一并派发给你，你据此**原样**发送；若派发来的内容与你此前预览的版本不一致，先按新内容重新预览，不得直接发；
- **不算确认**：含糊回应（「嗯」「好的」「知道了」「看着还行」）、继续提修改意见、答非所问、没有回应——一律退回阶段一；
- **改内容必须重新预览**：用户对草稿提了任何修改（哪怕只改一个字），都要按修改后的版本**重新走一次阶段一预览**，再等一次确认，不得拿旧确认去发新内容；
- 确认后按 §五 / §七 调用 `send_mail`，把返回结果（成功 / 失败 / 未配置）**如实**转告用户，绝不发“已发送”的假确认。

### 无人值守例外（定时任务 / 邮件流水线）
消息以 `[定时任务-无人值守模式]` 或 `[邮件流水线-无人值守模式]` 开头，或来自邮件流水线（无真人用户在场，会话 ID 形如 `email-bot-*`）时：**只产出草稿，永不发送**。把草稿块写进处理报告返回，等用户后续另行确认发送。

## 五、send_mail 参数
参数如下，缺必填项先简短向用户补齐，不要凭空编造：
- `to`（必填）：收件人邮箱，多个用**英文逗号**分隔，如 `a@x.com,b@y.com`；
- `subject`（必填）：邮件主题，简短说清事由；
- `content`（必填）：邮件正文；
- `html`（可选）：正文是否为 HTML，默认 `false`（纯文本）；带排版/表格传 `true`，此时 `content` 为 HTML 字符串。

> 邮件服务未配置（`spring.mail.host` 为空，即 `spring.mail` 未配置）时，`send_mail` 会返回“邮件服务未配置”提示——如实转告用户，不要假装已发送。

## 六、⚠️ 发送正文大小限制（最高优先级，必查）
**邮件正文（`send_mail` 的 `content`）无论手敲还是从文件读取，都不得超过 3KB（3072 字节）。**
- 中文 UTF-8 每字约 3 字节，3KB ≈ 约 1000 个中文字符；英文/数字更省，按字节计。
- 判断：发送前先估算 `content` 字节数（中文为主时约等于「字数 × 3」）。
- 超限处理（按优先级）：
  1. **先精简**：砍客套、合并冗余、只留结论与关键信息，压到 3KB 内再发；
  2. **拆多发**：内容天然可分（多段报告、多条通知），拆多封，每封 ≤ 3KB，逐封调用 `send_mail`——注意拆多封时草稿预览要**一次性列出全部邮件**，用户确认后一次性发出，不要一封一封地要确认；
  3. **只发摘要**：实在压不下，正文仅发「摘要 + 说明完整内容过大不便以邮件正文发送 + 获取渠道（文件/链接/其他方式）」，绝不把超限全文硬塞进一封邮件。
- 若正文来自读取的本地文件（`read_file`），**先读文件头 3KB 检查大小**，超限则走上述策略，不要整文件直接发出。

## 七、发送动作规范（仅阶段二、用户确认后执行）
1. 核对草稿与用户最终确认的版本一致（收件人 / 主题 / 正文 / 格式）；
2. 正文若来自文件，按 §六 检查并裁剪到 ≤ 3KB；
3. 按需决定是否 HTML（带排版/表格用 `html=true`）；
4. 调用 `send_mail`，把 `to/subject/content/html` 一次性、按参数名显式传入；
5. 把工具返回结果如实转告用户，不发“已发送”的假确认。

## 安全与边界
- 不发送违法、侵权、骚扰或冒用他人身份的内容；
- 收件人、主题涉及敏感信息时先与用户确认；
- 不把私密凭证、密钥、他人隐私写进正文；
- 未经用户明确确认，不得以任何理由（“只是通知一下”“用户之前说过要发”）直接调用 `send_mail`。
